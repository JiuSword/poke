# 双人桌游《女王万岁》技术方案文档

> Long Live the Queen · Dieselpunk Edition —— 微信小程序联机实现
> 作为现有「联机德州扑克」小程序的子模块,从主页横置入口进入。

---

## 1. 背景与目标

在现有微信小程序云开发项目(联机德州扑克)中,新增一个**风格独立的双人桌游**《女王万岁》,作为完整的联机对战功能。

### 范围与约束(已确认)
- **完整对战引擎**:骰子、数字条、角色能力、主谋/新兵、卫兵、声望、胜负判定全部实现。
- **仅双人对战**:房间固定 2 座。
- **不涉及积分**:纯娱乐,不消耗/不结算积分(不复用 settlement)。
- **不计时**:回合无超时(不复用 timer-scheduler)。
- **视觉风格独立**:蒸汽朋克/柴油朋克金属做旧风(深铁灰 + 黄铜 + 齿轮),不沿用德扑深蓝风。
- **角色卡面**:CSS + emoji 纯代码绘制。
- **代码隔离**:新代码完全独立,除主页加入口、app.json 注册页面外,不修改现有德扑代码。
- **支持中途退出重连**:玩家退出后可通过「历史房间」再次加入继续游玩。

## 2. 游戏规则模型(引擎权威定义)

### 2.1 棋盘
- 数字条位置 **2–12**(共 11 格)。位置 **7 = 公主初始位**。
- 公主**被翻成背面即该方失败**。
- 其余 10 格(2,3,4,5,6,8,9,10,11,12)各放 1 张角色牌,开局全部背面朝下。
- 每方 12 张牌:`公主` → 7 号;`主谋(Master)` → 侧边背面暗置;其余 10 张 → 上述 10 格随机铺放。
- 玩家**全程可查看自己所有牌(含背面)与主谋的真身**;对手背面牌不可见。

### 2.2 角色清单(initiative = 左上角先攻值)

| 先攻值 | 角色 | 声望 | 可当主谋 | 能力 |
|---|---|---|---|---|
| 1 | SNIPER 狙击手 | 红 | ✅ | +1红;翻面敌方**点对称**位置的牌 |
| 2 | ASSASSIN 刺客 | 红 | ✅ | +1红;翻面敌方**同位置**的牌 |
| 3 | SCHEMER 阴谋家 | 黄 | ✅ | +1黄;使对手退回 1 个声望 |
| 4 | NOBLE 贵族 | 黄 | ✅ | +1黄;再获得任意 1 个声望 |
| 5 | GAMBLER 赌徒 | 无 | ❌ | 从对手夺取 2 个声望(不足取其全部) |
| 6 | PRINCESS 公主 | — | ❌ | 翻开己方 1 张背面牌;自身被翻面即败 |
| 7 | PILOT 飞行员 | 蓝 | ✅ | +1蓝;交换己方相邻牌,最多 2 次 |
| 8 | ENTERTAINER 艺人 | 蓝 | ✅ | +1蓝;给对手 1 个声望,再从对手拿 1 个 |
| 9 | SPY 间谍 | 蓝 | ✅ | +1蓝;交换对手相邻牌,最多 2 次 |
| — | RECRUIT 新兵 ×2 | — | ❌ | 激活时翻开主谋并**继承主谋**的能力与先攻值 |
| — | GUARD 卫兵 | — | ❌ | 正面时**保护相邻**牌不被翻面(不保护自己) |

> 点对称映射(以 7 为中心):2↔12,3↔11,4↔10,5↔9,6↔8,7↔7。

### 2.3 回合流程
1. **掷骰**:两颗骰子求和(2–12),命中数字条同号位置,**双方该位置的牌同时受影响**。
2. **激活**(按位置上双方两张牌的状态):
   - A 都背面 → 都翻开,**不触发能力**。
   - B 都正面 → 都**触发能力**,按先攻值升序结算;**先攻值相同则都不触发**。
   - C 一正一背 → 先结算正面牌能力,再翻开背面牌。
   - 被翻面的牌本回合**不激活、不再翻回**。
3. **新兵规则**:激活 RECRUIT 时翻开主谋(若未翻开),以主谋能力与先攻值结算。
4. **声望规则**:
   - 集齐某色 **6 个**立即全部退回供应。
   - 供应耗尽则拿不到;从对手拿但对手没有则不拿。
   - 同色两张牌同回合都要拿、供应只剩 1 个 → 低先攻值者拿。
5. **重新布置(Reposition)**(回合末,可选,二选一):
   - 交换己方相邻两张牌;或
   - 更换主谋(用一张允许的正面牌与当前主谋交换)。
   - **先手玩家第一回合不可布置。**
6. **结束**:传骰给对手。

### 2.4 胜负
- **声望胜利**:集齐红、黄、蓝各 ≥ 3 个 → 立即获胜。
- **斩首胜利**:翻面对方公主 → 对方失败。

## 3. 整体架构

复用现有项目模式:
- 云函数统一返回 `{ code, msg, data }`;前端 `utils/cloud.js` 封装调用。
- `utils/db-watch.js` 的 `WatchManager` 负责实时 `watch` + 指数退避断线重连。
- 隐藏信息沿用德扑的「**服务端真相 + 公开视图 + 私有情报**」三集合思路。

```
主页 home ──横置入口──▶ queen/lobby(大厅:创建/加入/公开列表/历史房间)
                              │
                创建/加入 ────▶ queen/room(候场厅:双方准备、房主开始)
                              │
                  开始/重连 ──▶ queen/game(棋盘对战核心)
                              │
            ┌─────────────────┼─────────────────┐
       queen_rooms        queen_states       queen_private
       (公开视图,脱敏)    (完整真相,不可读)   (己方真身,仅本人可读)
            ▲                  ▲                  ▲
            └──────── 云函数 queen-room / queen-game 写入 ───────┘
```

## 4. 数据库设计

### 4.1 集合与权限规则

| 集合 | 读权限 | 写权限 | 说明 |
|---|---|---|---|
| `queen_rooms` | `auth.openid != null` | `false` | 房间元信息 + **公开棋局视图**(背面牌身份脱敏为 null),双方 watch |
| `queen_states` | `false` | `false` | 完整真相,客户端不可访问 |
| `queen_private` | `auth.openid == doc._openid` | `false` | 每玩家私有视图,仅本人可读(含己方所有牌真身) |

### 4.2 `queen_rooms` 字段
```
roomCode, hostOpenid, status(waiting/playing/finished/dismissed), isPublic,
players[2]{ openid, nickname, avatar, color(white/black), isReady, lastSeen },
memberOpenids[]   // 曾加入过的成员(历史房间查询 + 重连鉴权)
stateId, createdAt, lastActivityAt,
view: {           // 公开棋局视图(脱敏)
  phase, currentPlayerColor, dice{a,b,sum}, activePosition,
  board[pos]{ white{faceUp,role|null}, black{faceUp,role|null} },  // 背面牌 role 一律 null
  masters{ white{faceUp,role|null}, black{...} },
  prestige{ white{r,y,b}, black{r,y,b} },
  pendingChoices[], canReposition, log[], winnerColor, starterColor, turnCount
}
```

### 4.3 `queen_states` 字段(完整真相)
```
roomId, board[pos]{ white{role,faceUp}, black{role,faceUp} },
masters{white,black}, prestige, currentPlayerColor, starterColor,
phase, dice, activePosition, pendingChoices(完整), pendingActivations,
pendingFaceUps, canReposition, log[], winnerColor, turnCount, firstTurnDone
```

### 4.4 `queen_private` 字段(每玩家一份)
```
_openid, roomId, myColor,
myLine[pos]{ role, faceUp },   // 己方所有牌真身,含背面
myMaster{ role, faceUp }
```

### 4.5 建议索引
- `queen_rooms`:roomCode、status、lastActivityAt、memberOpenids + lastActivityAt
- `queen_private`:_openid + roomId(联合索引)

## 5. 云函数设计

### 5.1 `queen-room`(房间管理)

| action | 说明 |
|---|---|
| `createRoom` | 生成唯一 6 位房间号,房主入座(默认已准备),写入 memberOpenids。先调用 cleanStaleRooms 清理 |
| `joinRoom` | 第二人入座,房间满 2 人;追加 memberOpenids |
| `rejoinRoom` | **中途退出重连**:仍在座则刷新在线;已离座则按 `queen_private` 记录的原始颜色重新落座。返回 status 决定回候场厅还是进棋盘 |
| `leaveRoom` | playing 中离开**不解散**(保留重连);waiting 中离开解散空壳房 |
| `setReady` / `startGame` | 准备 / 房主开局(发牌、掷骰定先手、初始化三集合) |
| `dismissRoom` | 房主解散 |
| `getRoomInfo` / `listPublicRooms` | 房间信息 / 公开房间列表 |
| `listMyRooms` | **历史房间**:我曾加入、未解散(waiting/playing)的房间 |
| `heartbeat` | 30s 心跳,更新 lastSeen + lastActivityAt |

### 5.2 房间清理策略 `cleanStaleRooms`(每次创建房间时触发)
1. `waiting` 且 5 分钟无活动 → 解散(无人且未开始过)。
2. `playing` 且**创建超过 72 小时** → 解散;否则**保留**,支持成员再次加入继续游玩。

### 5.3 `queen-game`(对战引擎入口)

| action | 说明 |
|---|---|
| `rollDice` | 当前玩家掷骰 → 计算激活 → 自动结算无需选择的效果,需选择的压入待决策队列 |
| `resolveChoice` | 逐个提交玩家决策(owner 可能是非当前回合方,故不强制当前回合) |
| `reposition` | swap 相邻 / changeMaster |
| `endTurn` | 传骰,切换回合 |
| `surrender` | 认输 |

引擎模块:
- `lib/engine.js`:角色表、点对称映射、声望操作、翻面(含卫兵保护)、胜负判定。
- `lib/abilities.js`:激活流水线(`activatePosition`/`pumpActivations`)、能力结算(`applyAbility`)、待决策队列消费(`resolveChoice`)。
- `views.js`:`buildPublicView`(脱敏)+ `buildPrivateView`(己方真身),两个云函数目录各保留一份副本。

### 5.4 待决策队列机制
含玩家选择的能力(贵族选色、阴谋家退牌、赌徒抢牌、公主翻牌、飞行员/间谍换位、艺人给/拿)在 `rollDice` 后进入 `pendingChoices` 队列;前端逐个 `resolveChoice` 提交,引擎按先攻值顺序消费,消费后继续推进激活流水线。

| 页面 | 说明 |
|---|---|
| `lobby/` | 大厅:创建房间、输码加入、公开房间列表、**历史房间(继续游戏)** |

### 6.1 game 页双订阅合并
- watch `queen_rooms`(公开视图:对手 + 棋盘 + 状态)。
- watch `queen_private`(己方所有牌真身)。
- `rebuild()` 合并两者:己方牌优先用私有真身渲染(背面牌标「暗牌」,仅本人可见),对手背面牌渲染玫瑰背面。

## 7. 关键技术点 / 踩坑记录

### 7.1 云数据库 update 的点路径深度合并陷阱
**现象**:`Cannot create field 'activePosition' in element {view: null}`。
**根因**:微信云 DB 的 `.update()` 会把嵌套对象拍平成点路径深度合并(`view.activePosition`…),父字段为 `null` 时无法建子字段。
**解决**:
- `queen_states`、`queen_private` 用 `.set()` 整体覆盖文档。
- `queen_rooms.view` 用 `_.set(buildPublicView(state))` 整体替换该字段,绕过深度合并。

### 7.2 云函数写文档必须显式写入 `_openid`
**现象**:玩家看不到自己的背面牌/主谋(显示玫瑰背面)。
**根因**:`queen_private` 读权限是 `auth.openid == doc._openid`,但云函数用 `.add()`/`.set()` 写库**不会自动带 `_openid`**(仅客户端写库才自带),导致文档无 `_openid` → 被权限拦截读不到。
**解决**:`startGame` 与 `persist` 写 `queen_private` 时显式 `_openid: p.openid`。

### 7.3 case B 决策归属
**现象**:双方同位置正面牌都激活时,决策 owner 可能是非当前回合方。
**解决**:`resolveChoice` 不强制当前回合;前端决策弹层只要 `head.owner === myColor` 即显示。

### 7.4 隐藏信息脱敏
对手背面牌身份**只存在于 `queen_states`(不可读)**,公开视图 `queen_rooms.view` 中背面牌 role 一律为 null,绝不下发到客户端可读集合。

## 8. 验证方式(end-to-end)

1. 开发者工具上传部署 `queen-room`、`queen-game`;云开发控制台新建 3 个集合并按本文档配置权限规则与索引。
2. 主页确认「双人桌游」横置入口为蒸汽朋克风,点击进入大厅。
3. 两账号:A 创建房间 → B 输码加入 → 准备 → 开始。
4. 对战逐项验证:掷骰命中 → 翻开/激活 → 决策弹层(选色/翻牌/换位)→ 声望增减 → 点对称(狙击)、卫兵保护、刺客翻面、新兵继承主谋、先攻值排序、声望 6 封顶。
5. 胜负:制造「三色各 3」与「翻面对方公主」两种胜利。
6. 隐藏信息:确认对手背面牌公开视图 role 为 null,自己背面牌可见真身。
7. 重连:游戏中退出 → 大厅历史房间「继续」→ 恢复局面。
8. 断线重连:杀进程/切后台再回,WatchManager 自动重连。

### 引擎本地测试覆盖
引擎核心已通过本地 Node 单元测试(13 项断言):刺客同位翻面、狙击点对称、卫兵保护(含不保护自己)、斩首胜利、声望胜利、声望 6 封顶、新兵继承主谋、同先攻值不激活、case B 双方决策队列归属、JSON 序列化往返、脱敏不泄漏等。
